# Quality targets and evidence

Choose only the relevant dimensions below; detailed benchmark evidence is not required for an unrelated R1 cosmetic edit.

## Scores and verifiable evidence

Scores communicate judgment. Required acceptance checks and unresolved blocking findings decide readiness. Two high scores cannot offset a failed permission test or missing mandatory behavior.

### Agent-defined quality targets

Reuse the task’s already agreed quality targets. For missing targets, the agent owns routine discovery and definition before implementation or acceptance claims; do not restart a settled spec. The owner should not have to invent performance numbers, test cases or a design rubric for every task. The speccing agent investigates before implementation, records a compact quality contract in the existing spec, and lets the selected independent review challenge its adequacy. Tiny R1 tasks inherit applicable standards and need only the affected check, not a new quality document.

Use this evidence order: explicit user/project acceptance and existing budgets; design-system components, contracts and CI rules; a representative healthy comparable flow and measured baseline; applicable primary standards/guidance. The stricter applicable explicit requirement wins. An observed broken or slow existing flow is evidence of a problem, not the default quality bar. If no reference is adequate, the agent sets a justified provisional engineering target from the workload, platform and user journey, states its source/assumptions and tests it. Technical defaults do not require a user interview; actual product preferences, new visual directions and business tradeoffs still do. Do not claim a provisional target was previously approved or measured.

Choose the metrics, reference, workload, tolerance/noise policy and pass conditions before the task's acceptance benchmark and before implementation. A limited discovery measurement may inform the target; label it separately, then freeze the protocol and capture the recorded BEFORE. Do not retune the target after AFTER results to turn failure into success. Improvements must prove the requested gain as well as meet the applicable floor. No-regression is necessary where applicable, but insufficient when the baseline already violates the standard. Test target adequacy as part of review, not just whether the implementation passes an easy target.

| Task example | What the agent finds | Derived target and proof |
|---|---|---|
| New web page | Project budgets and relevant Web Vitals guidance | Respect project budgets. Where applicable, use LCP ≤2.5s, INP ≤200ms and CLS ≤0.1 as initial field targets at p75, segmented by mobile/desktop. Controlled lab runs are useful proxies, not proof of a field p75 pass. Record dataset, conditions and any missing field evidence. |
| New form/dialog | Existing healthy form, design tokens, accessibility requirements | Reuse established components and spacing; no horizontal overflow at supported viewports; keyboard completion, visible focus, useful validation and loading/error states. Check normal text contrast ≥4.5:1 (large text ≥3:1) with applicable exceptions; pointer targets follow the 24×24 CSS px minimum or its specified spacing/other exceptions. These checks alone do not prove full WCAG conformance. |
| Improve an existing UX journey | Current steps, errors, persistence, accessible states | Complete the requested journey and retain entered data through recoverable errors. Match or reduce the relevant steps/errors within the predeclared comparison. UI ratings use the same written rubric before/after and remain agent judgments, not human-usability evidence. |
| New/improved API/search endpoint | Existing SLO, request traces/query plans, healthy comparable endpoint, data size/concurrency and access rules | Define timing, query/work, payload/resource and correctness/leakage targets using the API scorecard below. Reuse justified project budgets; do not copy a universal latency or query-count threshold. |
| Data change | Existing schema/API rules and explicit expected records | Assert exact fields, identifiers, relationships and permissions; reject duplicates/unauthorized access where applicable. Counts/sums alone cannot establish correctness. |
| Tiny button-colour fix | Requested colour, design tokens, contrast and affected states | Verify the requested appearance and affected contrast/focus/hover/disabled states. No full performance benchmark or Council unless the change introduces a relevant risk. |

Sources for the external examples: [Google Web Vitals](https://web.dev/articles/vitals), [W3C contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), and [Google SRE user-journey/SLO examples](https://sre.google/workbook/implementing-slos/). API/data/UX targets above are DevStack engineering examples, to be derived for the actual project, not universal numeric standards.

For each required dimension record target, evidence/source, scope, test method, actual result and limitations. Required but not verified means pending/blocking, not Yes and not a measured failure. A product with no field telemetry can use a justified controlled-test acceptance contract where that is sufficient for the actual task; it cannot claim a field SLO pass. Missing genuinely required evidence prevents Full Send closure and causes an explicit blocker/handoff when it cannot be obtained. N/A needs a concrete applicability reason.

### API quality scorecard: timing, queries and no leakage

For API performance improvements, lead with measured time and database/network work. The agent chooses the relevant metrics and targets from the actual request path, workload and reported bottleneck. Preserve the response contract and access boundaries. A faster endpoint that returns less required data, skips authorization, shifts excessive work to another service or creates a resource leak does not pass.

| Dimension | What to capture and verify |
|---|---|
| Speed | End-to-end request latency and server/database breakdown where available; median and p95, p99 only with adequate samples. Separate successful, failed and timed-out requests rather than excluding slow failures. For an affected frontend journey, measure user-visible completion too. |
| Query and request work | Database queries per request or complete journey, cumulative DB time, expensive query plans/rows examined where safely observable, N+1 growth, duplicate queries and downstream HTTP calls. Compare representative small/large datasets and pagination sizes; fewer queries alone is not proof of less work or lower latency. |
| Payload efficiency | Bytes transferred and necessary fields/records; verify pagination, compression/cache behavior where relevant. Do not obtain smaller payloads by dropping required results or returning private fields for the client to filter. |
| Reliability and capacity | Errors, timeouts, retry amplification and throughput at stated concurrency; inspect relevant CPU/memory/connection-pool saturation. Keep workload and infrastructure comparable. A single fast request does not establish behavior under load. |
| No data/access leakage | Executed positive and negative checks for role, tenant, object and field permissions. Inspect relevant response/error/cache behavior for unintended exposure using synthetic markers and safe assertions, not copied private data. Cached responses must respect identity and permissions. A passing finite test matrix establishes those tested boundaries, not universal absence of leakage. |
| No resource leakage, when relevant | Repeated-request/soak behavior for retained memory, connections, handles, listeners or unfinished work. Distinguish warmup/GC and bounded pooling from continuing growth. Do not claim a soak result from a short smoke test. |
| Correct data and contract | Exact expected records/values, ordering, filtering, pagination, error semantics and required side effects under the applicable contract. Aggregate totals alone cannot establish correctness. |

Capture BEFORE and AFTER with the same request mix, dataset, concurrency, relevant identity/permission context, build/environment and cache state. Declare cold/warm runs, warmup, sample count, measurement window and comparison/noise rules. Retain safe raw measurements and trace identifiers; never retain credentials, tokens or raw sensitive query/response data. Controlled workload generation must use an authorized test target and test-owned fixtures; no unapproved production load or data writes.

The chat evidence card shows actual before → after latency, queries/request, relevant DB time, payload and errors, plus explicit permission/data-check verdicts and limitations. Plot a latency distribution/percentiles or before/after bars when that helps; show raw artifact links. No invented improvement percentages or numeric leakage score. The claimed optimization must improve its intended metric under the declared protocol while satisfying the other required budgets and checks. Record a justified tradeoff explicitly; do not silently exchange correctness/security for speed or enforce fewer queries as a universal goal.

This metric selection follows [Google SRE monitoring guidance](https://sre.google/sre-book/monitoring-distributed-systems/); field/property exposure checks are informed by [OWASP API property-level authorization guidance](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/). The concrete scorecard and targets are DevStack policy, scoped to the actual task.

Measurement-validity checks belong to testing, before trusting or reporting a number: confirm the work ran inside the measured region, count failures, identify the limiting resource/path, compare equivalent tuned configurations, account for noise and connect the measured component to the end-to-end result. Use separate profiling runs when instrumentation distorts timing. Repeat/alternate comparable runs enough for the claim; a one-run estimate remains labeled an estimate. Retro consumes these results to explain friction and improve the workflow after the task. It does not replace measurement validation or add a second benchmark pass. Borrow the discipline from [pstack's benchmark checklist](https://github.com/cursor/plugins/blob/main/pstack/skills/benchmark-checklist/SKILL.md), adapted to actual task size.

Every feature gets two explicit verdicts: **“Feature works? Y/N”** and **“Meets the project quality standard? Y/N.”** The second verdict needs evidence for each applicable dimension below. A feature that works but fails its UI, UX, performance or data requirement is not ready. Mark missing evidence as **not verified**, never an invented Yes or a claimed observed failure.

Use one applicable quality bar for new features, improvements and fixes. New features must meet the approved design/interaction standard, performance budgets and data correctness expectations, using comparable existing flows where useful. Improvements additionally need matched before/after evidence for their claimed gains, and affected existing behavior must not regress beyond agreed tolerances. If a dimension is genuinely inapplicable, record N/A with a reason in the proof contract; it is not an escape from a failed requirement. For example, an API-only change may have no UI surface but still needs its applicable performance, data, permission and contract checks.

| Aspect | Evidence | Comparison rule |
|---|---|---|
| Feature works? Y/N | Acceptance assertions, negative cases and real interaction | Verify the requested outcome on the integrated result as well as individual slices. Report functional success separately from quality acceptance. |
| Good UI | Screenshots, approved design-system/reference comparison, responsive states and a fixed visual rubric | New and changed UI must meet the same approved bar. Use matched before/after views for improvements. Label ratings as agent judgments, not objective measurements. |
| Good UX | Task completion, errors, steps, accessibility, loading/empty/error states and rubric | New and changed flows must meet the same interaction expectations. Separate observed metrics from model opinion. Human usability is not proven without human evidence. |
| Performance: fast enough / faster when required | Raw timings, sample count, median/tail latency as appropriate, build/environment and protocol | New features meet agreed budgets or comparable-flow targets. Improvements use the same workload, dataset, device/network controls and method before/after. Show variation and regressions alongside gains. |
| Data | Expected records, field values, permissions and network/API behavior | Check exact results and counterexamples, not only counts or sums. Screenshots alone cannot establish data correctness. |
| Security/context/scale | Executed tests/scans or explicit source-based analysis | Label measured results separately from reasoning. “Production-ready” and “scales” need relevant evidence, not a generic model score. |

Benchmark and quality results should carry task/criterion ID, run ID, spec/protocol version, repo and before/after SHAs, build/environment, fixture identity, browser/device/viewport where relevant, actual tool/model, command or steps, raw artifact paths, units, sample count, score rubric where used, result and limitations.

Show a compact before/after evidence card in chat and link the raw artifacts from the issue/PR. Missing BEFORE evidence means no defensible measured improvement claim. If it can be reconstructed safely in an isolated checkout, do so; otherwise label the limit. Scores and targets must not be weakened after seeing the result just to achieve a pass.

The feature evidence card includes functional Y/N, each applicable quality dimension's target and result, evidence links, and the overall quality verdict. A brand-new feature can prove quality against its agreed targets without claiming to be faster or better than a nonexistent previous implementation.

### New features include quality work

SPEC and the work breakdown include the implementation **and** its quality proof: performance budget/measurement, approved UI pattern and responsive states, UX journey/accessibility/error-state coverage, and exact data/permission assertions. These are explicit acceptance/work items, owned by the relevant implementer/verifier, rather than optional polish after a functional pass. They can be grouped into a coherent slice and checked concurrently where practical; they do not require four new agents or four serial tickets.

Use the approved product standard and comparable flows. A new screen that happens to load has not passed UX, performance or data quality. API-only work records genuinely inapplicable UI checks and still proves its relevant contracts, performance, data and permissions. New features, fixes and improvements retain the same applicable quality bar; proof effort follows the actual change and risk.

### Project verification recipes extend testing

Use or maintain project-scoped verification recipes for repeatable app/API/CLI journeys: check readiness and the intended build/environment, launch if necessary, drive the real path, assert visible behavior and relevant side effects, retain evidence and clean only owned test state/processes. Prefer existing tests/harnesses; create a new recipe only when an actual reusable gap warrants it. The NEW [create-test-recipes](../../create-test-recipes/SKILL.md) generator is adapted from pinned current Poteto source, not the old installed skill. It creates and maintains the project verification pack. Execute each new/changed recipe in the requested scope, report any unrun coverage explicitly, and distinguish faithful recipe validity from an application failure it detects. PR/local proof and live proof remain separate. The worker/tester selects relevant journeys; maintaining the recipes adds no serial gate or new global orchestration layer. The replaced create-verification-skill is archived outside discovery; this generator is the active replacement.
