# Mode and decision ownership

Full Send/Full Stop controls Patrick's involvement and delivery endpoint. Size, urgency and R1/R2/R3 control execution effort and proof. R3 does not by itself mean Full Stop.

## Full Send: own the answer

The lead first uses the available brief, project conventions and prior relevant tasks/decisions. Investigate unresolved facts through source, actual runtime, primary research or a cheap discriminating experiment as appropriate. These are options for resolving uncertainty, not a mandatory four-stage research ceremony.

If evidence still leaves ordinary uncertainty, choose the safest useful, reversible in-scope default and proceed. Record the assumption and validate the outcome. Do not ask Patrick to decide routine architecture details, technical targets, equivalent implementation options or facts the lead can establish. Prefer an existing approved product/design pattern when taste is unsettled. Continue through PR, required checks, configured test delivery and live verification; the exact test-delivery grant is defined in [testing/delivery](testing-delivery.md).

Proceeding under uncertainty means performing a defensible action and checking it. It does not mean calling missing proof a pass, bypassing permissions, guessing the target environment or ignoring a failed security/acceptance check. Failures enter repair. An exhausted ordinary approach calls for a new hypothesis, not abandonment or another interview by default.

Keep the explicit gates Patrick retained: significant new visual direction uses browser alternatives for approval; preference changes to the shared workflow involve him; production and destructive/out-of-scope actions retain their actual permissions. Reuse approvals already given. Vault unlock/MFA that cannot be completed by an available authorized mechanism is an access dependency, not a product question. Continue useful independent work while the affected part waits.

## Full Stop: include Patrick where it matters

Keep Patrick involved at meaningful product/approach decisions and leave the ready PR unmerged for his review. Still resolve observable facts and ordinary implementation details autonomously. A human checkpoint states the decision, evidence, recommendation, consequences and work that can continue; avoid vague requests for confirmation.

## Choosing the mode

Default development tasks use Full Send. Preserve Patrick's standing intake rule: a very large/important task with meaningful sensitive auth/permissions, important shared API or broad customer-facing impact can be classified Full Stop before implementation. Explain the actual impact. A cosmetic change in such a repo does not qualify by filename alone. If Patrick explicitly selects Full Send for the actual task, keep that mode within its granted scope and retained gates; use appropriate review depth for its risk. Never switch to hands-on simply because two technical options remain possible.

A verified new impact meeting the sensitive/important criteria during execution raises review depth and gets one human decision checkpoint (as in Full Stop) for the affected high-impact decision; ordinary uncertainty does not qualify. An explicit Full Send choice remains in effect within its actual scope and retained gates. Continue unaffected work while the decision waits.
