# Ticket references and native coordination

Tickets are references only. Reuse the task's existing `TKT-…`; for a genuinely new designated task use `~/.local/bin/ticket-ref new` (Windows: `ticket-ref.cmd new` or Python with the installed script). Read [numbering usage](../../../tools/ticket-ref/README.md) for bootstrap. The lead and its agents normally share the same reference. Pass it in briefs, native chat titles, Issue/PR links and handoffs. Independent deliverables may get separate numbers; reviews and session starts do not.

**Agents issue numbers; people never do.** A person asks for the work. The lead agent allocates the number, puts it in its native title at once, and carries it into every brief, branch name, Issue and PR title. People refer to a task by its number and never run `ticket-ref` themselves.

**Tickets on a team board.** When the checkout ships a `monday.json` (a project pack) or the owner has `~/.config/patstack/monday.json`, a new ticket is a subitem on that board and its number comes from [`tools/monday_ticket.py`](../../../tools/monday_ticket.py).

**Scope: that board and nothing else.** The config names one workspace and one board. Agents touch Monday only through `monday_ticket.py`, which proves on every run that the board sits in that workspace and refuses otherwise. Never create boards, test boards, columns or items anywhere else, never write in another workspace, and never point the tool at another board, with any tool or API call. When a task seems to need anything outside the board, refuse and ask the owner. Test Monday code with fakes or read-only.

Steps:

1. `python3 <patstack>/tools/monday_ticket.py check`. If it fails because no token is set up, set it up now: open the token page that `monday_ticket.py setup` prints in the person's browser, ask them to create and copy a personal API token, take it through the host's private secret input (in T3, `request_secret` with file delivery; never in chat), run `monday_ticket.py setup --store <that file>`, and check again. Never print, log or commit the token.
2. Run `monday_ticket.py parents` (read-only JSON lines) and choose the roadmap item this work belongs to. When no item clearly fits, ask the owner with the native question tool, offering the likely items. Never create roadmap items yourself.
3. `monday_ticket.py new --parent <item id> --title "<short title in the board's language>"` prints `TKT-<n> <subitem id> <link>`. Use the number everywhere, and put the link in the brief and the PR: the subitem ID in it is the ticket's identity, the number is its label.
4. `tools/task_status.py` sets each status on the subitem right after its own ping (a few seconds at most, and it says so when Monday did not take it); `monday_ticket.py link TKT-<n> <PR URL>` posts the PR. `monday_ticket.py find TKT-<n>` looks a ticket up.
5. Monday has no lock, so two subitems can, rarely, end up with one number. The tool then refuses the number and lists each subitem. Pass `--item <subitem id>` with the ID that `new` printed for your ticket (the tool refuses an ID that does not hold the number), and have the newer ticket (higher ID) take a fresh number with `monday_ticket.py renumber --item <id>`; its lead then updates the thread title, branch and PR title.

If Monday cannot be reached, continue as `[TKT-pending]` and allocate before opening the PR. Without any Monday config, use the machine counter below.

**Set up a machine (the agent's job).** When `ticket-ref new` reports that the counter is not initialized on this host, the lead sets it up before allocating:

1. Ask the owner, with the native question tool, which ticket slot this machine was given. The Patstack maintainer hands out slots, one per machine, from the [slot table](../../../tools/ticket-ref/SLOTS.md). Never pick a slot yourself, and never reuse another machine's slot.
2. Choose `--after` from real history: the largest `TKT-` number in PR and Issue titles across the GitHub owners the team works in (for example `gh search prs TKT --owner <owner> --limit 1000 --json title --jq '.[].title'`, and the same with `gh search issues`), plus 1000 as margin for numbers that only ever appeared in chat titles. The margin also stops a reinstalled machine from reissuing its own earlier numbers.
3. Run `python3 <patstack>/tools/ticket-ref/ticket_ref.py init --slot <n> --owner <label> --after <number>` and `python3 <patstack>/scripts/ticket_launcher.py install --apply`, then `ticket-ref new`.
4. Report the slot, the `--after` value and the first number in the task's report.

A missing counter never blocks continuing a task that already has a number.

**Find a ticket again.** Numbers are permanent and never reissued, and the counter holds no task content, so a task is found where its number was written: `gh search prs "TKT-<n>" --owner <owner>`, `gh search issues "TKT-<n>" --owner <owner>`, branch names `tkt-<n>/…`, and native thread titles (in T3, `t3_thread_search`). That is why the number goes into the title the moment it exists.

A number grants no permission: any capable agent on any host can work on any referenced task. The issuing host is a number namespace, never a permission or ownership marker. Existing references remain valid.

## Enter or resume

Read the actual request, accepted spec/Issue and later steering; bind the project, environment and current worktree. Use the number once, not a new ticket per phase or agent. Keep the goal, scope, mode, acceptance, head/build/release, evidence, participants, repair history and next action in the existing Issue/brief/native task record ([continuity](task-state.md)). No second execution database is introduced. Discussion, research and casual testing stay unticketed unless designated as work.

Shared files and releases are coordinated through the brief and current participants. Check for active work and uncommitted changes; preserve it, agree who integrates overlapping edits and use isolated worktrees when useful. This is practical collaboration, not a lock or permission check. Resume at the earliest valid phase and preserve credit. A new session or different machine never resets attempts, grants authority or changes the ticket's identity.

## Delegate and communicate

One lead coordinates one child layer. Choose actual available models/tools for the task: the person's ranking per job in `~/.config/patstack/preferences.json` first (set by [start-here](../../start-here/SKILL.md)), else the [team defaults](../../../MODEL_RANKING.md); both are advice, not eligibility rules. Small work stays direct. A child gets the ticket reference, accessible spec/version, project/worktree, files, actual model/runtime/tools, allowed actions, dependencies, acceptance, proof and stop conditions. Children preserve others' work and do not start agents or top-level chats. Review independence covers the actual contributions; model agreement is not execution proof.

Use the host's native delegation and run events under its current tool contract. Inspect ambiguous dispatch outcomes before retrying and preserve returned IDs/idempotency keys; queued is not delivered. Share context through native results and existing task artifacts, with no secrets/private browser records. Existing peer/Claude bridge tools remain transport where applicable, never task or deployment authority.

## T3 Code tools

Follow the live injected T3 contract and exposed schemas; availability and policies vary by runtime. Relevant deferred tools must be discovered before calling a capability absent. Prefer native subagents for same-provider work when the current contract permits; use `delegate_task` for cross-provider/background/isolated or explicitly delegated work as specified by the host. Use live model capabilities when required. Each new independent delegated review is a new task; fix small findings directly when the host says so. Do not turn a child backing thread into a fresh review round. Follow a running delegate's returned continuation instructions; do not invent polling or new top-level chats.

- PRs: link each created/taken-over/pushed PR immediately using exposed `link_pull_request`, including stack layers. Handle current findings first. When required work waits on checks/reviews, the lead calls `watch_pull_request` and ends the turn; native events wake it. Children do not watch. Unwatch before handback. CLI-created PRs still need linking.
- Browser work: in T3 the browser panel (`preview_*`) is the default route for web UI proof, before desktop or computer-use routes. Follow the live browser contract: start with `preview_status`, then `preview_open` if needed; use snapshots and focused interactions. Never type a password into the panel (it would sit in the tool call): the person signs the test persona in once in the panel's normal profile, which keeps the session, and the agent works in that session; checks without a browser use the project's secret-safe login tool. Say so when the panel cannot do a check, and name the host that can ([Patstack in T3](../../../docs/t3.md#4-testing-web-ui-the-browser-panel)). Respect human/agent tab ownership. Parallel browser agents use separate tabs and their returned IDs. Follow the documented fallback threshold and retain the actual error. Do not use preview tools for own edits when the host prohibits it.
- Devices: use exposed `device_list`/`device_open` and the exact returned launcher/context for native proof. A model name does not establish device access.
- Visuals: use `html_preview` then `html_render` when the current host requests inline charts/flows; exported assets belong in the requested repo/file. Do not invent a phase/progress-bar setter.
- Secrets and schedules: use private secret-input tools when required; never chat credentials. Persistent schedules/top-level conversations are created only when requested. None grants deployment or external-message authority.

## Delivery and authority

A ticket number, agent role or tool call grants no permission. Preserve actual project AGENTS/DEPLOY rules, explicit task grants, native client approvals, branch protection and data/production boundaries. Full Send covers the task's established, unambiguous authorized test target and repair revisions, plus the project's own production on an INTERNAL [tier](../SKILL.md#choose-the-mode); Full Stop stops at the ready PR after R2 or R3 for a human to merge, and needs explicit authority for production or destructive data effects. Auto-deploying merges are deployments. Production needs its actual explicit authority.

### Merge

In **Full Send** the lead merges its own ready PR, and only through the merge gate, which protects the default branch: `python3 tools/merge_gate.py merge --repo OWNER/NAME --pr N`. The gate reads the PR from GitHub, checks the rule below for the exact head and merges exactly that head through GitHub's synchronous merge endpoint, which can neither queue the PR nor arm auto-merge. In **Full Stop** a human merges: the lead finishes the R2/R3 review, publishes its records and findings on the PR, confirms with `python3 tools/merge_gate.py check --repo OWNER/NAME --pr N` that the rule holds for the head and stops at the ready PR ([Full Stop](../../full-stop/SKILL.md#endpoint)); the gate's `merge` refuses a Full Stop PR. The PreToolUse guard [`tools/merge_guard.py`](../../../tools/merge_guard.py) refuses any shell command whose words include `gh` with `pr merge`, or `gh api` with any word containing `merge`, or any raw `gh api graphql` call, wherever they stand; text that only names them together is refused too and is rephrased. Risk raises review depth and proof; it never lowers the mode's minimum.

- **Review before merge, by mode.** Full Send needs at least R1, and R2 where [review](../../review/SKILL.md) or the project's risk map requires it (trust boundaries; the risk classes a project pack names); R3 is allowed but rare. Full Stop needs an in-depth review: R2, or R3 for broad, irreversible or high-impact changes.
- **Verified review.** A review counts only through its record: a separate PR comment whose whole body is this one line for the current head, posted by the review session (by the author for R1); the summary and findings go in another comment:
  `Patstack-Review: level=R2 verdict=approve head=<sha, at least 12 characters> reviewer=<provider/model> session=<review session or task id>`
  A session that ran under a [reviewer lens](../../review/references/lenses.md) appends ` lens=independent` or ` lens=adversary`. R2 and R3 need the `Patstack-Author: <provider/model>` header line. R2 counts from a reviewer of another provider, or from the author's provider under a lens; R3 counts with approvals from two providers, or from one provider under both lenses. Prefer the other provider whenever it is available. The latest record of a reviewer session replaces its earlier ones; a standing `verdict=block` blocks. A new commit needs new records, with one exception, a repair after R2: in Full Send with a required depth of R2, the author's R1 record on the new head with ` repairs=<reviewed sha>` reaches R2 when that sha is an earlier commit of the PR, an independent R2 or R3 record exists for it, it is the latest reviewed head and no reviewer record on it carries ` recheck=independent` ([review](../../review/SKILL.md#r2)). Full Stop and R3 keep a fresh review of the exact head.
- **Declared depth.** When the lead selects a review above the mode's floor (for example R2 for a Full Send change at a trust boundary), the header says so with `Patstack-Level: R2|R3`, and the gate then requires that depth. Without the line the gate enforces the floor only.
- **What the gate proves.** Agents post under the GitHub account of the person running them, so records are self-asserted: the gate proves that a well-formed record for the exact head exists at the required depth from a declared independent provider or lens, not which session wrote it. Because a record must be a whole one-line comment, an example in a code block, quote or summary never counts.
- **Header.** The PR body starts with `Mode: Full Send — …` or `Mode: Full Stop — …` (risk, review depth and proof, and whether a revert undoes it), followed by the optional `Patstack-Author:` and `Patstack-Level:` lines, each once, plain text at column 0 ([file-pr](../../file-pr/SKILL.md)). Only this header declares anything; the same words elsewhere in the body or in a comment do not count. To change the mode, edit the header.
- **Length.** The whole body, header included, stays at or under 200 words, so a person reads it. Evidence and repair history go in a [PR comment](../../file-pr/SKILL.md#evidence-comment), and editing the body needs no new review.
- **CI.** CI runs in the agent, on the task's own PR, in every repository, and the lead never adds a GitHub Actions workflow anywhere. The repo's CI is its `scripts/ci-local.sh` (or `scripts/ci_local.py`), and once the head is pushed the lead runs `python3 tools/local_ci.py --path <worktree> --repo OWNER/NAME --pr N --runner <provider/model>` without being asked. The tool combines the PR head with the base branch's current commit in a throwaway worktree and runs the script as the person running it (their files and stored GitHub login stay reachable; only credential-like environment variables are dropped), so it runs only same-repository PRs whose author can push. It then posts a one-line `Patstack-CI: result=pass|fail head=<sha> runner=<provider/model> base=<sha>` record with full SHAs. The gate needs the latest record for the exact head, posted by an account that can push to the repo, to pass on the base's current commit: a new commit on the head or the base needs a new run, and no statement in the body stands in for the record. The gate re-reads the base just before merging and refuses if it moved; GitHub cannot make the merge itself conditional on the base, so if the base moves in that last moment the gate exits 3 and says so, and the lead runs local CI on the base branch at once. PRs merge with `--method merge` or `squash`, never `rebase`, so a repo that allows only rebase merges has to allow one of the two first. The gate merges directly or not at all: a base branch with a merge queue is refused, because a queued merge lands later on a base local CI did not test, and such a PR goes to a human. A red local CI is repaired like any failed check, never skipped. **A repo without the script gets one in the same PR** ([what the script runs](../../create-test-recipes/SKILL.md#the-repos-ci-script)). **Repos without GitHub Actions.** A repo whose owner or `OWNER/NAME` the [tier map](../../../examples/project-tiers.example.json) lists under `local_ci` runs no GitHub Actions at all: no test, build, deploy, sync or scheduled workflow. The gate does not read GitHub checks there, and a file left under `.github/workflows/` is removed in the same PR or one of its own: checks move into the script, and a deploy, sync or scheduled job moves to the agent or a timer on a host the team runs, as the project's deploy procedure says, before its workflow file is deleted. **Other repos.** Workflows that other contributors run stay as they are: their checks on the head must also pass (pending or failed ones block), and the lead neither removes nor edits them unless the task says so.
- **Mergeable.** Open, not a draft, no conflicts.
- **Authority the gate does not grant.** A merge that deploys to production, or that applies a destructive or irreversible data operation (deletes, reseeds, migrations without a rollback) to a shared environment, needs explicit task-specific authority quoted on the PR before the gate runs, in either mode; without it the task stops at the ready PR and hands off. On an INTERNAL project the [tier](../SKILL.md#choose-the-mode) named in the mode line is that authority for a deployment to the project's own production, not for a destructive data operation. Nothing here overrides stricter project rules, branch protection or a retained human approval gate (for example a project's own mainline approval), and GitHub auto-merge stays off. The gate covers GitHub; other forges follow their project procedure with the same checks.

Record the real assignment, mode basis, target and applicable head/release in the Issue/PR or existing brief. Quote genuine approval when required. If a project's own procedure still needs updating, preserve its real approval requirement and report the specific obsolete integration instead of inventing an actor permission.

Finish when the requested endpoint, required review/checks, actual release proof and proportionate Retro are complete. Cancelled children and stale revisions cannot block completion. A real missing acceptance check, capability or approval remains a real blocker; report Done / Verified / Unresolved / Next without claiming missing proof.
