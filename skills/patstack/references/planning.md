# Plan only what the task needs

Reuse an accepted spec. Resolve project context and existing issue/branch first. A tiny explicit request can be its own brief; do not manufacture a spec file, task graph or interview.

For larger work, record goal/non-goals, acceptance, relevant constraints, intended test delivery and meaningful risks in the existing shared spec/Issue. The lead distributes an accessible version to workers; [project context](project-context.md) defines sharing without routine application-repo spec clutter. Derive only missing [quality targets](quality.md) from project evidence. Preserve user-selected behavior and approved visual direction.

Freeze the acceptance/measurement protocol, then capture BEFORE or a red reproduction. A new feature can use missing behavior as its baseline and absolute quality targets. Do not invent a comparative speedup for a nonexistent previous feature.

Split only independently verifiable work that benefits from parallel execution. Each ready slice gets one owner, exact scope/worktree, dependencies, spec version, model/tool capability, acceptance, test method and stop conditions. Only the lead starts children; children return results and objections rather than spawning another management tree. The lead remains responsible for integration and the full outcome.

For a significant new visual direction, present browser-based options at Patrick's retained approval point. For other uncertainty, use [mode decisions](decisions.md); Full Send defaults to a researched, tested in-scope choice.
