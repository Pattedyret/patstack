# Patstack in T3 Code

T3 Code runs Claude Code and Codex as threads in one app, per project. Patstack works there unchanged: the same skills, global instructions and checks. This page covers what is different in T3 and what to set up once. The general setup is [onboarding](onboarding.md); `/start-here` does both.

What the table below says was observed in T3 (server 0.1.9-nightly) with probe threads in a fresh project, on 2026-11-10.

| | Claude in T3 | Codex in T3 |
|---|---|---|
| Finds the skills in the opened folder (`/start-here` in a fresh clone) | yes, from `.claude/skills` | yes, from `.agents/skills` |
| Asks you questions with options | `AskUserQuestion` | `request_user_input_async` in normal mode; `request_user_input` only in Plan mode |
| Merge guard blocks a direct pull request merge | yes | **no, until you trust it once in a terminal** (below) |
| Browser panel tools (`preview_*`) | yes | yes |
| Thread title as ticket (`t3_thread_update`), `T3CODE_THREAD_ID` set | yes | yes |

## 1. Set up T3 once

1. **Install T3 Code** and sign in.
2. **Connect your providers** in T3: Claude (your Claude subscription) and/or Codex (your ChatGPT subscription). Each person uses their own logins.
   - With **both** providers, an R2 review runs on the other provider than the one that wrote the change.
   - With **one** provider, R2 and R3 run as fresh sessions of that provider under the [reviewer lenses](../skills/review/references/lenses.md). That is supported, so you don't need the other subscription.
3. **Add projects.** One T3 project per folder you work in:
   - your Patstack checkout, where you run `/start-here`;
   - each product repository you work on.

   Clone a repository first, then add the folder. A project's threads start in that folder. T3 can give a thread its own worktree, which keeps parallel tasks apart.
4. **Runtime mode.** Patstack expects agents that can run commands and edit files, so use *full access* for normal work, or *auto* if you want to approve some actions yourself. Full access is tool access only. It grants no permission: production, destructive data operations, merges and deploys keep their gates.
5. **Run `/start-here`** in a thread in the Patstack project (in Codex: `$start-here`). It sets everything else up and asks how you want to work.

## 2. Trust the Codex merge guard in a terminal

Codex runs a new hook only after you trust it. The Codex terminal app asks at startup ("Hooks need review"). **T3 does not show that question**, and Codex then skips the hook without a word. In the probe, a Codex thread in T3 ran a direct merge command unblocked, while a Claude thread was blocked.

Do this once per machine, after `/start-here` has added the guard:

```bash
codex          # in a terminal, not in T3
```

Choose **Trust all and continue**, or review it under `/hooks`, then quit. Codex stores the trust in `~/.codex/config.toml`, which the Codex in T3 reads as well, so T3 threads should block from then on. That last step was reasoned from where Codex keeps the trust, not observed in T3. Step 6 of the practice task checks it on your machine with a harmless `echo` command. `scripts/setup_doctor.py` shows `codex merge guard` as `OK` once Codex has recorded the trust; until then it is `WARN`.

## 3. Day to day

- **Tasks:** ask for a change in a thread. The agent takes a ticket number, puts it in the thread title (`[TKT-…] Short title`), and works through planning and review to the end point. Where the task is shows in the agent's task list in the thread: the whole plan, with the step in progress and what it waits on.
- **Questions:** decisions and access come to you through the question tool, as clickable options, or as a status `🔴 WAITING ON YOU` with the exact action named.
- **Secrets** (an API token, a pairing code) go through T3's private secret input, never through chat. The agent asks for it with the secret card and never prints the value.
- **Pull requests** are linked to the thread, so T3 shows their state.
- **Several agents:** the lead starts child agents (another model for review, parallel work) as child threads. You can read them but don't need to.

## 4. Testing web UI: the browser panel

In T3, web UI checks run in T3's **browser panel**, the `preview_*` tools. It is a real browser that the agent drives, and you can watch it. It is the default route for web UI proof in T3, before any desktop or computer-use route.

- The agent opens the page, takes snapshots, clicks and types, and reads the console and network traffic.
- **Test logins:** an agent never types a password into the panel, because the password would end up in its tool call. Sign the test persona in yourself, once, in the panel's normal profile; it keeps the session. Use the project's test-persona logins, never your own account. The agent then works in the logged-in panel and asks you again when it needs another persona. Checks that need no browser (API calls) use the project's secret-safe login tool instead.
- When the panel cannot do the check (native apps, several windows, a specific operating system), the agent says so and names the host it needs.

## 5. When something is off

| Symptom | Fix |
|---|---|
| A Codex thread merges without the guard stopping it | Section 2: trust the hook in a terminal |
| `/start-here` is not offered | The thread is not in the Patstack project folder; open a thread in that project |
| The agent cannot ask you a question in Codex | Normal mode uses `request_user_input_async`; if it is missing, the agent asks in chat |
| The browser panel shows "not available" | Nothing is open yet: the agent opens a tab with `preview_open`, and the panel then reports available. Open the T3 window to watch it |
| The task list stops changing | The task ended or is waiting for you; the step in progress names what it waits on, and the last message says the rest |
